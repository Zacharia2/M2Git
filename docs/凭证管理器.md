# 凭证管理器技术文档
> 模块：M2Git 凭证（Credential）子系统
> 覆盖：数据模型、数据库层、UI 层、认证重试链路、已知边界与检修指南
> 最后审查结论：无阻碍正常使用的已知 bug（错误框叠压问题已豁免）
> 核对状态：弹窗层、任务回调层已与代码逐行核对；数据库层/管理器层基于此前审查结论，个别条目标注【待核验】

## 1. 架构总览
```
┌─────────────────────────────────────────────────────────────┐
│ UI 层                                                        │
│  CredentialActivity        凭证管理器（列表/新建/编辑/关联）  │
│  BaseCompatActivity        认证弹窗（选择器 + 手动输入）      │
│  凭证列表 Adapter           列表展示（secret 掩码）           │
│                            【待核验：Adapter 具体类名】       │
└──────────────┬──────────────────────────────────────────────┘
               │ 调用
┌──────────────▼──────────────────────────────────────────────┐
│ 数据层                                                       │
│  RepoDbManager    单例，所有 DB 读写 + DB_LOCK + 观察者通知   │
│  RepoContract     表结构 + Cursor 取列工具                   │
└──────────────┬──────────────────────────────────────────────┘
               │ 映射
┌──────────────▼──────────────────────────────────────────────┐
│ 模型层                                                       │
│  Credential       不可变载体（int id, account, secret, rel）  │
│  Repo             运行时凭证状态（temp/pending）+ 任务管理    │
└─────────────────────────────────────────────────────────────┘
认证触发侧：
  RepoOpTask (abstract)
    └─ RepoRemoteOpTask (implements OnCredentialEntered)
         └─ CloneTask / PullTask / PushTask / FetchTask ...
```
**两套凭证状态，职责不同：**
| | 存储位置 | 生命周期 | 用途 |
|---|---|---|---|
| **持久凭证** | SQLite `credentials` 表 | 永久 | 管理器展示、弹窗选择列表 |
| **运行时凭证** | `Repo` 对象内存字段 | 单个 Repo 对象存活期 | 当前任务的即时认证 |

## 2. 数据模型
### 2.1 credentials 表

| 列 | 类型 | 说明 |
|---|---|---|
| `_ID` | INTEGER PK AUTOINCREMENT | 从 1 递增；**`-1` 是约定的"无 id"哨兵值**（`_unrelateRepoFromAllCredentials` 的 `exceptId`、`pendingId` 两处） |
| `token_account` | TEXT | 账号名，**唯一约束**（`SQLiteConstraintException` 兜底预检重名） |
| `token_secret` | TEXT | token/密码，**明文存储**（UI 掩码只防瞟一眼） |
| `rel_repo` | TEXT | 逗号分隔的 repo id 串，如 `"3,7,12"`；空串 = 无关联 |
**核心设计：仓库与凭证的关联数据源就在 credentials 表的 rel_repo 列**，repo 表中没有反向引用。删除凭证行 = 关联自然失效；删除仓库时由 `_deleteRepo` 主动解除关联。
### 2.2 Credential 模型（`core/models/Credential.java`）
不可变对象，唯一构造入口是 `new Credential(cursor)`，字段直接从 Cursor 读取（经 `RepoContract` 取列）。`getDisplayName()` 返回 `账号 (#id)` 格式，用于弹窗列表和管理器列表。
### 2.3 Repo 上的运行时凭证字段
| 字段/方法 | 含义 |
|---|---|
| `setToken()` | 任务启动时初始化：temp → 查表 → 匿名，逐级回退 |
| `setTempCredential(u, p)` | 手动输入的即时凭证，不落库 |
| `setPendingCredential(id, u, p)` | **选已有凭证**时调用：整体覆盖（含清除旧 pendingId），id 用于成功后落库关联，account/secret 立即生效 |
| `clearPendingCredential()` | 手动输入取代所选凭证时，废弃 pendingId（防双重关联） |
| `saveCredentials()` | `persistCredentials` 的包装 + 置 `mTempCredential=false`；**只清标志不清字段** |
| `getUsername()/getPassword()` | 当前生效的凭证值 |

## 3. 数据库层（RepoDbManager）
### 3.1 并发模型
- 所有复合读写都在 `synchronized(DB_LOCK)` 内；
- `notifyObservers` 在锁内触发是**安全的**——观察者经 `runOnUiThread` 异步切主线程，不会死锁；
- 主线程同步查询是有意为之（表仅个位数行），**不要"优化"成异步**。`getAllCredentials` 是弹窗流程的同步依赖点（见 §4.2），改成异步会破坏弹窗时序。
### 3.2 关键方法分区
```
单例 → 观察者 → [仓库: 查询/写入/_私有] → [凭证: 查询/写入/关联维护/_私有]
```
凭证区重点方法（⚠️ 基于此前审查，检修前建议对照实际实现）：

| 方法 | 行为要点 |
|---|---|
| `createCredential(account, secret)` | 同名命中时**返回旧 id**，由调用方决定是否覆盖 secret |
| `overwriteCredential(id, secret, mergeRepos)` | mergeRepos 是**并集**合并【待核验：secret 传 null 是否表示"不动 secret"，此处行为未在代码中证实】 |
| `persistCredentials(repoId, u, p)` | ① 先 `_unrelateRepoFromAllCredentials(repoId)` 解除旧关联 → ② 建/更新凭证 → ③ `relateRepoWithCredential`。**跳过空 u/p** |
| `relateRepoWithCredential(cid, repoId)` | 去重追加；凭证行不存在时安静返回（竞态兜底） |
| `setCredentialRepos(cid, set)` | 整体替换 rel_repo（管理器"关联仓库"多选保存用） |
| `_unrelateRepoFromAllCredentials(repoId, exceptId)` | 统一版；`exceptId=-1` = 不排除。先收集后批量写回，避免边遍历边改表 |
| `getAllCredentials()` | 主线程同步查询，弹窗与管理器共用 |
| `pruneOrphanCredentialRelations()` | 清理 rel_repo 中指向已删除仓库的 id；**仅在打开凭证管理器时调用**；updatesMap 为空时不再 notify（防递归，天然收敛） |
| `queryCredentialByRepoId(repoId)` | 认证时查可用凭证（返回 Map），主线程调用 |
| `findCredentialIdByAccount(account)` | 重名预检（精确匹配） |
| `deleteCredential(id)` | 只删 credentials 行，关联随之失效，无额外清理 |

## 4. UI 层
### 4.1 CredentialActivity（管理器）
- **列表**：`getAllCredentials()` + Adapter（secret 掩码显示）；
- **新建**：同名预检 → 命中则弹**确认对话框** → 用户确认后 `createCredential`（返回旧 id）+ **并集合并** rel_repo；
- **编辑**：对话框预填 account；**secret 留空 = 不修改**（`credential_secret_keep_hint`）；重名走 `SQLiteConstraintException` catch 兜底（预检已挡大部分）；
- **删除**：`deleteCredential` → observer 通知刷新 → 重新 prune（幂等，第二轮空 updates 不再 notify）；
- **关联仓库多选**：draft 副本上勾选，保存时才 `setCredentialRepos` 整体写入；
- **数据刷新链**：DB 变更 → `notifyObservers` → `notifyChanged()` → reload → prune →（如有变更）再次 notify。
### 4.2 BaseCompatActivity（认证弹窗）
两条弹窗路径，**均有 `isFinishing() || isDestroyed()` 守卫**：
```
promptForCredential(listener, errorInfo)      ← 任务认证失败入口
  └─ promptForCredentialInner
       ├─ 凭证表为空 → 直接 showManualEntryDialog
       └─ 非空 → 列表选择器（列出全部凭证，不按关联过滤）
             ├─ 点条目 → onCredentialPicked(creds[which])
             ├─ "手动输入" → showManualEntryDialog
             └─ "取消" → onCanceled()
showManualEntryDialog → promptForPassword → promptForPasswordInner
  └─ "完成" → onClicked(u, p, saveChecked)
```
凭证查询在主线程同步执行（有意为之，见 3.1）。

## 5. 认证重试链路（核心时序）
### 5.1 触发与回调
```
doInBackground
  └─ JGit 抛异常含 "Auth fail"/"auth"
       └─ handleAuthError(listener=this)
            ├─ 非认证错误 → return（不弹窗）
            └─ promptForCredential(this, errorInfo)   [后台线程入队主线程]
onPostExecute → showException（已知豁免：可能叠在选择器上面）
```

### 5.2 三条用户路径的落库行为
| 路径 | 关键动作 |
|---|---|
| **选凭证** `onCredentialPicked` | `setPendingCredential(id, u, p)`（整体覆盖，无残留问题）→ `getNewTask()`（此时读旧 repo 的 u/p 透传）→ execute；**成功后的 pendingId 落库关联在各子类的 onPostExecute 中实现（如 CloneTask），基类 RepoOpTask.onPostExecute 不含落库逻辑** |
| **手动输入** `onManualEntered` | 空值拦截 → `clearPendingCredential()`（**防双重关联的关键行**）→ `setTempCredential` → `getNewTask()` → **`saveCredentials` 落在新 repo 上**（保证 rel_repo 写的是活 id）→ execute；成功后 pendingId==-1，子类 onPostExecute 不重复落库 |
| **取消** `onCanceled` | 什么都不做；克隆的失败清理由 doInBackground 兜底 |
### 5.3 CloneTask 特殊性（历史上 Bug 1 所在）
克隆失败时 `doInBackground` 会 `deleteRepoSync` 删掉旧仓库行 → **旧 repo 的 id 已死**。因此：
- 手动保存必须落库到 `getNewTask()` 的新 repo；
- 顺序约束：`setTempCredential` 必须在 `getNewTask()` **之前**（否则透传丢失）；
- `getNewTask()` 只能调用一次。
  Fetch/Pull/Push 的 repo 始终存活，三条路径行为一致。

### 5.4 已验证的边界矩阵

| 场景 | 结果 |
|---|---|
| 选 C1 失败 → 再选 C2 成功 | pendingId 被 C2 覆盖，单关联 |
| 选 C1 失败 → 手动 B+保存成功 | pendingId 已清，只关联 B |
| 手动 B+保存 → 失败 → 删 101 | `_deleteRepo` 自动解除关联 |
| 手动错密码 → 失败 → 改正再保存 | 同名命中 + secret 更新 |
| 弹窗期间 Activity 销毁 | 守卫拦截 |
| 凭证在弹窗展示期间被删 | 快照可用；落库时安静降级 |

## 6. 已知边界与非 bug 行为（检修时先对照这里）

| 现象 | 原因 | 处置 |
|---|---|---|
| 错误对话框压在凭证选择器上 | `onPostExecute` 的 showException 在选择器入队后执行 | **已豁免不修**；如将来要修：`RepoOpTask` 加 `mAuthRetryPending` 标记 |
| 删仓库后立刻认证，可能先用旧凭证试一次才弹窗 | `queryCredentialByRepoId` 命中悬空关联，自动尝试旧凭证 → 失败后才弹选择器；**弹窗列表本身不受影响**（它列出全部凭证） | 正常行为；悬空关联等下次打开凭证管理器时 prune 修正 |
| 非认证错误偶发弹出选择器 | `toLowerCase().contains("auth")` 匹配偏宽 | 用户取消即可，无害 |
| token 明文存 SQLite | 设计取舍 | UI 掩码防瞟；在意云备份可加 backup rules 排除 databases/ |
| 主线程同步查凭证表 | 表极小，有意同步 | 不要改异步 |
| 历史双重关联脏数据 | 旧版"选凭证失败→手动输入保存"未清 pendingId 所致（已修复） | prune 只清无效 id，**清不掉重复有效 id**；存量脏数据需一次性手动清理 |

## 7. 检修指南（按症状定位）

**症状 A：仓库操作总是弹认证，选了凭证下次还是弹**
→ 检查 `rel_repo` 是否写入了正确 id：`adb shell` 查看 credentials 表。落库关联在**各子类的 onPostExecute**（先查 CloneTask 等，基类 RepoOpTask 里没有）。若克隆场景，重点查 `onManualEntered` 是否落库到 `newTask.mRepo`（而不是死掉的旧 repo）。
**症状 B：一个仓库出现在多个凭证的关联里**
→ 历史上是"选凭证失败 → 手动输入保存"时 pendingId 未清导致。确认 `onManualEntered` 里有 `mRepo.clearPendingCredential()` 且位置在 `getNewTask()` 之前。现存脏数据 prune 清不掉（只清无效 id），需手动清理。
**症状 C：凭证管理器列表不刷新 / 刷新死循环**
→ 检查 `pruneOrphanCredentialRelations`：updatesMap 为空必须不再 notify（收敛条件）；以及 `notifyChanged` 是否被注册到正确 table key。
**症状 D：新建凭证报"账号已存在"**
→ 这是唯一约束 + `saveCredential` 预检的正常路径；若误触发，确认 `findCredentialIdByAccount` 的查询条件（精确匹配）。
**症状 E：弹窗崩溃 BadTokenException**
→ 确认 `promptForCredentialInner` 和 `promptForPasswordInner` 都有 `isFinishing() || isDestroyed()` 守卫。
**症状 F：克隆重试时凭证丢失（匿名重试）**
→ 检查 `onManualEntered`/`onCredentialPicked` 中 `setTempCredential`/`setPendingCredential` 是否在 `getNewTask()` **之前**调用。
**并发类问题** → 确认所有复合操作在 `DB_LOCK` 内；`_unrelate*` 是"先收集后批量写"模式。

## 9. 修改时的红线清单
1. **改 `persistCredentials` / `_unrelate*` 前**先读本文档 §5.3——三个调用方（克隆/删除/覆盖）语义不同；
2. **不要给弹窗查询加异步**——`getAllCredentials` 的同步结果是弹窗流程的依赖；
3. **`getNewTask()` 在每个回调里只能调用一次**；
4. **`onManualEntered` 中三个动作的顺序不能乱**：clear → set → getNewTask；
5. **prune 的 notify 必须以"有实际变更"为条件**，否则观察者刷新链死循环；
6. 凭证 id 的哨兵值是 **-1**，`rel_repo` 解析时先过滤空串再 split；
7. **不要给 `onCredentialPicked` "对称地"加 `clearPendingCredential`**——`setPendingCredential` 整体覆盖，不存在残留问题；加了虽无副作用，但会误导后来者以为存在残留；
8. **落库关联逻辑在子类 onPostExecute 中**——改认证成功后的落库行为时别只看 `RepoOpTask`。
